# S4 HARA 分析规则

> 本文件是 S4 阶段（HAZOP → HARA）Agent 推理的核心参考。
> 输入：`s4_hara_skeleton.json`（由 `hara prepare` 生成）
> 输出：`s4_hara.json`（Agent 填写 events 后交 `hara validate` 验证）
> ASIL 由脚本计算，Agent 不填；ID 由脚本分配，Agent 不管编号。

---

## 1. 总体流程

> **代码强制机制（重要）**：先按 `agent_action` 分流。Domain Pack exact 或 S3 来源案例 exact 会生成 `locked` 组；其完整事件已由代码锁定，Agent 不参与。
> `similar/template/none` 或 `create_needs_review_events` 才需要 Agent 按当前项目证据审核、修改或创建事件。
> 禁止把案例库已覆盖的 `locked` 事件降级为 Agent 推理任务，也禁止为了通过验证而手工补写锁定事件。

对 skeleton 中每个 hazard 组：

1. **检查预填状态**：
   - `agent_action="locked"` 或 `prefill_locked=true`：完整 event（包括 description、scenario、S/E/C及理由、safety_goal、safe_state、ftti）已锁定，**禁止任何修改**
   - `source_case_locked=true`：事件由 S3 的 `source_case_ids` 解引用；validate 会再次读取案例资产逐字段比对，Agent 不得删除、重排或改写
   - 每个 event 有 `sec_source` 字段标注 S/E/C 来源：
     - `reference_exact`：从参考数据库精确匹配（388场景），**90%+ 正确**，只需确认
     - `reference_pattern`：模式匹配预填（转向域），需填理由和 description
     - `agent_evaluated`：无参考数据，Agent 按第 4-6 节评定
   - `prefill_locked=false`（未识别功能类型）：Agent 需按第 2-3 节自行展开场景
2. **确认/微调 S/E/C**：检查预填值是否合理，如需调整在 `note` 说明理由
3. **填写缺失理由和描述**：仅处理未锁定事件；`case_library_exact` / `domain_pack_exact` 的理由和 description 不得补写或改写
4. **确认安全目标**：检查预填的 `safety_goal` 是否正确，ASIL≥A 时必须有安全目标
5. **特殊情况**：工程判断例外（第 9 节）设置 `engineering_override: "QM"`
6. **禁止事项**：
   - 禁止修改 `safe_state`（安全状态）和 `ftti`，validate 会检查并报 error
   - 禁止修改 `scenario` 文本
   - 禁止对所有事件使用相同的 S/E/C（validate 会报 warning）
   - 禁止删除预填场景（会报 warning）
   - 禁止使用 `--force` 跳过验证
   - validate 有 error 时 `write` 命令将拒绝生成 Excel

## 2. 危害类型识别

| 危害类型关键词 | 危害类型 | 说明 |
|--------------|---------|------|
| 横向运动、转向、偏离车道、侧滑 | `lateral_steering` | 转向系统异常导致非预期横向运动 |
| 溜车、纵向移动、车辆移动 | `rollaway` | 驻车/保持失效导致车辆非预期移动 |
| 横向运动（制动导致）、不对称制动 | `lateral_braking` | 制动力不对称导致横向运动 |
| 减速、制动、追尾 | `longitudinal_decel` | 行驶中非预期制动导致减速 |
| 无法移动、不能行驶、卡滞 | `immobilization` | 车辆无法移动 |
| 制动距离、制动效能、制动力不足 | `brake_loss` | 制动能力丧失或不足 |
| 报警、提示、指示灯 | `warning_loss` | 报警/提示功能丧失 |

一个失效模式可能导致**多种危害类型**，每种危害类型独立展开场景。
例如 EPB 非预期接合同时导致 `lateral_braking`（不对称制动横向运动）和 `longitudinal_decel`（纵向减速）。

### 2.1 强制规则：危害类型必须从 HAZOP 危害描述推导

**禁止从异常表现猜测危害类型。** 必须读取 skeleton 中该 hazard 组的 `hazard` 字段（即 HAZOP 的"整车危害"列），根据危害描述选择场景集。

常见错误：EPB"非预期接合驻车制动器"的异常描述含"接合"，Agent 误选 immobilization（无法移动）场景。但 HAZOP 危害描述是"非预期车辆横向运动"和"车辆非预期纵向减速"，应选 `lateral_braking` + `longitudinal_decel`。

### 2.2 EPB 失效模式→危害类型→场景集强制映射

| 异常表现 | HAZOP危害 | 危害类型 | 场景集 | 场景数 |
|---------|----------|---------|--------|-------|
| 接合驻车制动器功能丧失 | 车辆非预期纵向移动 | `rollaway` | 3.2 溜车 | 12 |
| 释放驻车制动器功能丧失 | 车辆丢失纵向运动 | `immobilization` | 3.5 无法移动 | 1（城市道路起步，S=0） |
| 非预期接合驻车制动器 | 非预期车辆横向运动 | `lateral_braking` | 3.3 制动不对称横向 | 3（高速/湿滑/路口转弯） |
| 非预期接合驻车制动器 | 车辆非预期纵向减速 | `longitudinal_decel` | 3.4 非预期纵向减速 | 3（高速/城市/路口） |
| 非预期释放驻车制动器 | 车辆非预期纵向移动 | `rollaway` | 3.2 溜车 | 7（与接合丧失的12个不同，侧重行驶中释放） |
| 动态制动非预期激活 | 车辆非预期纵向减速 | `longitudinal_decel` | 3.4 非预期纵向减速 | 7 |
| 驻车制动不足 | 车辆非预期纵向移动 | 引用 | 引用接合丧失 | 1行引用 |

### 2.3 制动失效模式→危害类型→场景集强制映射

| 异常表现 | HAZOP危害 | 危害类型 | 场景集 | 场景数 |
|---------|----------|---------|--------|-------|
| 车辆制动功能失效 | 车辆减速度丧失或不足 | `brake_loss` | 3.6 制动效能丧失 | 9 |
| 车辆制动功能非预期激活 | 车辆非预期纵向减速或减速过度 | `longitudinal_decel` | 3.4 非预期纵向减速 | 9 |
| 车辆制动功能非预期激活 | 车辆非预期横向运动 | `lateral_braking` | 3.3 制动不对称横向 | 3 |
| 车辆制动过度 | 车辆非预期纵向减速或减速过度 | 引用 | 引用非预期激活 | 1行引用 |
| 车辆制动不足 | 车辆减速度丧失或不足 | 引用 | 引用制动功能失效 | 1行引用 |

## 3. 场景速查表（优先，脚本自动查询）

脚本在 `hara prepare` 时会按以下优先级自动预填场景。案例库 v2 先按跨项目语义匹配；旧场景表不得覆盖 v2 的匹配结果：

- 案例库 v2 的匹配键是 canonical domain、canonical function family、失效模式/异常类别、危害类别和场景语义指纹。
- 当前项目 `func_id`（包括 `F16`、`P_func_0001`）和 `failure_id` 只用于追溯，不能作为案例库匹配键；Domain Pack 中的来源项目失效 ID 也不得复制到当前项目。
- exact 才能锁定；similar/template 必须返回候选并保持可编辑，场景缺失不得伪造 exact。
- template 只表示功能族级参考；若异常、整车危害或场景与当前项目不一致，必须使用当前项目证据修正，禁止机械复制第一条候选的 S/E/C。
- F16 这类自定义编号必须通过显式 `--domain`、文档模板域或 Domain Pack 功能语义解析；无法解析时显式失败，不得生成 `unknown`。

脚本在 `hara prepare` 时会按以下优先级生成事件：

1. **Domain Pack exact 或 S3 来源案例 exact**：完整事件锁定；S3 `case_ids` 必须展开全部来源案例，Agent 不参与。
2. **Domain Pack compatible**：作为受控参考基线，Agent 只能确认或逐项登记项目差异。
3. **案例库 semantic similar/template**：仅在 S3 没有受控来源案例时使用，保持可编辑并展示候选。
4. **旧域兼容路径**：只有非 PT 域且没有 v2/Pack 资产时，才可使用当前域场景文件、域级 Profile 或迁移兼容总表。
5. **Agent 自行展开**：仅在以上来源确实均未覆盖时执行；不得把案例库已有数据当成 unknown。

速查表条目包含：标准场景列表、安全目标、安全状态、FTTI、S/E/C 评定要点（guidance）。Agent 填写 S/E/C 时应参考 guidance 字段。

> 速查表数据来源于 11 个数据组的交叉验证，目前覆盖 4 个域共 20 个功能类型：
> - **PT域（动力）**：驱动扭矩、制动能量回收、滑行能量回收、档位控制（D/N/P/R）
> - **AD域（智驾）**：横向控制、纵向控制、泊车控制（车内/车外）、驾驶辅助
> - **ET域（座舱）**：信息显示、娱乐系统、驾驶员/乘员监测、通信互联
> - **BD域（车身）**：外部灯光、雨刮、门窗、后视镜、座椅调节、安全装置
>
> 转向/EPB/制动等底盘域功能由硬编码场景集覆盖（见第4节），不在速查表中重复。

### 4.1 转向横向运动（lateral_steering）— 19 个标准场景

适用于所有转向相关功能（转向助力、转向角传感器等）。

| # | 场景 | 典型S | 典型E | 典型C |
|---|------|-------|-------|-------|
| 1 | 车辆处于静止状态 | 0 | - | - |
| 2 | 从停车位驶出时，在车辆前方有行人，驾驶员左转/右转 | 1 | 4 | 1 |
| 3 | 十字路口左转/右转，前方道路有车辆 | 1 | 4 | 1 |
| 4 | 在有障碍物的道路上行驶 | 3 | 2 | 3 |

| 6 | 在有急弯的道路上低速行驶，路边有行人 | 2 | 3 | 1 |
| 7 | 在高速道路上直线行驶，附近有车/路边 | 3(非预期)/0(丢失/过度/反向/卡滞) | 4 | 3(非预期)/0(丢失/过度/反向/卡滞) |
| 8 | 在乡村道路上高速行驶中变道，路边有行人 | 3 | 2 | 3 |
| 9 | 在乡村道路上高速行驶中变道，对面有来车 | 3 | 2 | 3 |

| 12 | 在弯曲的道路上低速行驶，附近有行人 | 2 | 4 | 1 |
| 13 | 在弯曲的道路上中速行驶，附近有行人 | 3 | 3 | 2 |
| 14 | 在弯曲的道路上高速行驶，附近有行人 | 3 | 3 | 3 |
| 15 | 在弯曲的道路上低速倒车，附近有行人 | 2 | 4 | 1 |
| 16 | 在弯曲的道路上低速行驶，附近有车/路边 | 1 | 4 | 1 |
| 17 | 在弯曲的道路上中速行驶，附近有车/路边 | 2 | 4 | 2 |
| 18 | 在弯曲的道路上高速行驶，附近有车/路边 | 3 | 4 | 3 |
| 19 | 在弯曲的道路上低速倒车，附近有车/路边 | 1 | 4 | 1 |

**关键规则**：
- 场景 7（高速直线）：转向助力**丢失**时 S=0（驾驶员不需要转弯，无事故）；**非预期**时 S=3/E4/C3=D（系统自主激活导致突然转向）；**过度/反向/卡滞**时 S=0（驾驶员直线行驶无转向输入，故障不表现，无事故）
- 场景 13、14（中/高速过弯+行人）：E 可从 E4 人工降为 E3（行人在弯道高速出现概率较低），需在 E 理由中注明
- 转向助力**丢失**时所有车速场景 C=0（机械转向备份始终可用，驾驶员可保持方向控制），ASIL=QM；仅急弯低速（场景 6）可 C=1（S2/E3/C1 仍为 QM）
- 转向**非预期**时 C 通常为 1-3（系统自主激活导致突然转向，驾驶员反应时间短）
- 转向**过度/反向/卡滞**时 C 通常为 1-3（非预期转向，驾驶员反应时间短），但高速直线场景 S=0

- 新项目增加了雨天场景，Agent 可根据功能特点增删场景并注明

### 4.7 报警/提示丢失（warning_loss）

不固定场景。多数报警丢失 S=0（报警本身不直接导致伤害）或 C=0（驾驶员可通过其他方式察觉）；S=0 时 ASIL 留空，S>0 且 C=0 时为 QM。
少数关键报警（如制动故障报警）可能 ASIL A，需根据具体报警内容分析。

### 4.8 新危害类型

如果 hazard 描述不属于以上任何类型：
1. 从 `reference-scenarios.md`（144 条参考场景库）中选择相关场景
2. 结合工程判断补充场景
3. 在 note 中注明"新危害类型，场景由 Agent 推理"
4. 人工审核后可将该场景集沉淀到本文件

### 4.9 反照搬规则（重要）

1. **禁止直接复制其他失效模式的场景集**。每个失效模式必须根据自身的异常表现和危害描述选择场景，即使危害类型相同，场景也应有差异。
2. **同危害类型的不同失效模式，场景可以重叠但不得完全相同**。例如 EPB"接合丧失"和"非预期释放"都是 rollaway，但前者是驻车后溜车（驾驶员可能离车），后者是行驶中或临时停车时释放（驾驶员通常在车内），场景侧重点不同。
3. **场景数必须与危害严重程度匹配**。高危害失效模式（如驱动扭矩丢失）应展开更多场景（参考27个），低危害的可少（1-4个）。禁止所有失效模式使用固定数量的场景。
4. **validate 阶段会检测不同 failure_id 之间场景完全重复的情况**，重复率 100% 将报 WARNING。

### 4.10 座舱/信息娱乐域（ET/Info）— 全 QM 域处理规则

座舱域（仪表、HUD、娱乐、账户、监测、手机互联等）绝大多数失效不直接导致安全危害，参考 Excel 中全部事件 ASIL 为空或 QM，整车安全目标 Sheet 无数据。但 **HARA 事件必须全部列出**，不能因为 QM 就跳过。

**核心规则**：
1. **每个预填场景都必须生成 event**，即使评定结果为 S=0 或 QM。S=0 事件写入 HARA 表（E/C 按规则填写），只是不分配安全目标。
2. **S=0 场景**：只有车辆确实始终保持静止、且该失效在此状态不表现或不会造成伤害时才取 S=0；E/C 及其理由填 null，ASIL 留空。不能仅因场景文本包含“静止”就强制 S0，例如“减速至静止后反向转矩”“停车静止时热失控/溜车”仍可能为 S>0。description 必须写明无危害理由。
3. **S=1/QM 场景**：行驶中信息显示丢失/非预期显示等，可能分散注意力但不影响车辆控制，S=1，E/C 按实际评定，ASIL 通常为 QM。
4. **少数需关注的场景**：
   - 车速表丢失在高速行驶时 S=1-2（驾驶员无法获知车速）
   - 驾驶员监测丢失（疲劳预警失效）S=1-2，需评估 E/C
   - 乘员监测丢失（儿童遗留检测失效）S=1
   - X-call/紧急求救丢失在事故场景 S=2-3（碰撞后无法求救），需评估 E/C
5. **safety_goal 一律填 null**（ET 域无 ASIL≥A 的事件），禁止编造安全目标文本。
6. **safe_state/ftti 填 null**（QM/S=0 事件不需要）。
7. **description（G列）必须填写**：参考 Excel 的写法是用一句话描述该场景下为什么不会有危害，例如"车辆行驶中，不显示车速，但车辆行驶性能没有变化，用户可以正常控制车辆做出正常操作，不会有危害事件。"

**禁止行为**：
- 禁止因为 guidance 写了"QM"就把整个 hazard 组设为 `skip=true`
- 禁止删除预填场景
- 禁止给 QM 事件编造 safety_goal
- 禁止将 ET 事件评为 ASIL A/B/C/D（除非有充分的安全危害论证）

## 5. S（严重度）评定规则

### 5.1 J2980 ΔV 速度表

| 碰撞对象 | S0 | S1 | S2 | S3 |
|---------|-----|-----|-----|-----|
| 车辆正面/追尾（ΔV km/h） | <10 | 10-30 | 30-60 | >60 |
| 车辆侧面（ΔV km/h） | <3 | 3-15 | 15-30 | >30 |
| 行人/两轮车（ΔV km/h） | <3 | 3-10 | 10-25 | >25 |

### 5.2 特殊规则

- **无事故/车辆静止** → S0，G 列写"车辆原地静止，无事故"或"由于驾驶员没有转弯，无事故"
- **高速直线+转向过度/反向/卡滞** → S0（驾驶员直线行驶无转向输入，故障不表现），G 列写"由于驾驶员没有转弯，无事故"
- **坠崖/冲出道路** → 直接 S3
- **80-100 km/h** → 取 Max{碰撞表结果, S2}
- **>100 km/h** → 直接 S3
- **碾压行人** → S3
- S=0 时 E/C 及其理由不评定（填 null），ASIL 必须留空（Excel N 列留空）

### 5.3 I 列（S 理由）写法

```
与行人发生高速碰撞（25<ΔV）
S3:危及生命的伤害(生存不确定)或致命伤害
```

或：

```
S0:没有受伤（车辆保持静止）
```

## 6. E（暴露概率）评定规则

### 6.1 等级定义

| 等级 | 持续时间占比 | 频率 |
|------|------------|------|
| E1 | <1% 运行时间 | <1 次/年 |
| E2 | 1-10% | 数次/年 |
| E3 | >10% | ≈1 次/月 |
| E4 | 高频 | ≈每次驾驶 |

### 6.2 评定方法

1. 将场景描述拆解为基本要素（道路类型、速度、交通参与者、天气等）
2. 每个要素在 `reference-scenarios.md` 中匹配 E 等级
3. **多要素组合取最低 E**（最不常见的要素决定整体暴露率）
4. K 列逐条列出：`E4:高速公路\nE4:行驶速度(60<v<120)\nE4:相邻车道有车`

### 6.3 人工降级

罕见组合可在工程判断基础上降级 E，但必须在 K 列注明原因。
例如：中速过弯+行人，基础 E4，但行人在弯道中速出现概率较低，降为 E3，注明"中速过弯时行人出现概率较低，E4降为E3"。

## 7. C（可控性）评定规则

### 7.1 等级定义

| 等级 | 定义 | 可避免比例 |
|------|------|-----------|
| C0 | 总体可控（每个驾驶员都能控制） | 100% |
| C1 | 简单可控 | >99% |
| C2 | 正常可控 | 90-99% |
| C3 | 难以控制或不可控 | <90% |

### 7.2 关键因素

- **速度**：高速 → C 升高（更难控制）；低速 → C 降低
- **失效突发性**：非预期突然发生 → C 升高；渐进式 → C 降低
- **驾驶员是否在环**：驾驶员在车内可踩制动/打方向 → C 降低；驾驶员离开 → C=3
- **替代措施**：有机械备份（如液压制动）→ C 降低
- **转向助力丢失特例**：机械转向备份始终可用，所有车速场景下驾驶员均可保持方向控制 → C0（仅急弯低速可 C1，仍 QM）

### 7.3 M 列（C 理由）写法

```
高速行驶中非预期横向运动，驾驶员反应时间极短
C3:不到90%的驾驶员能够避免伤害
```

或：

```
在此速度下，所需的转向扭矩远小于驾驶员的转向能力
C0:总体来说是可控的
```

## 9. 安全目标、安全状态、FTTI

### 9.1 安全目标模板（P 列）

| 危害类型 | 安全目标文本 |
|---------|------------|
| 转向横向运动 | 防止车辆非预期横向运动 |
| 转向卡滞 | 防止车辆横向运动失控 |
| 溜车 | 防止车辆非预期纵向移动 |
| 制动不对称横向运动 | 防止车辆非预期横向运动由于动态制动非预期激活 |
| 行驶中非预期减速 | 防止车辆非预期减速由于动态制动非预期激活 |
| 制动效能丧失 | 防止制动效能丧失（按具体功能描述） |

### 9.2 安全状态/FTTI 配置（Q/R 列，脚本预填，Agent 确认）

| 功能类型 | 安全状态 | FTTI |
|---------|---------|------|
| 转向助力 | 关闭转向辅助 | 非预期/过多/反向 200ms；卡滞 100ms；丢失无 SG(C=0) |
| 行车制动(IBS) | 1.IBS不使能; 2.制动力矩由机械液压部分驱动 | 500ms |
| EPB | 非预期接合→释放驻车制动器；非预期释放/不足→驻车制动器不得释放；动态制动非预期→动态驻车制动不使能 | 500ms |
| 车辆保持 | 丢失保持→保持驻车保持力；非预期保持→不提供车辆保持力 | 1s |
| 报警提示 | 发送对应提示 | 2s |
| ESC | 1.IBS不使能; 2.制动力矩由机械液压部分驱动 | 500ms |

### 9.3 填写规则

- ASIL=QM（仅适用于 S>0 的 QM 事件）时：P/Q/R 列留空（safety_goal/safe_state/ftti 填 null）。S=0 时 N 列必须留空，且 E/C 及其理由必须为 null。
- ASIL≥A 时：P 列填安全目标文本，Q/R 列确认预填值
- 脚本未识别功能类型时：Q/R 列为 null，Agent 需手动填写
- **每个非 QM 事件分配独立 SG ID**（即使 SG 文本相同），编号由脚本在 validate 阶段分配
- EPB 安全状态按危害方向自动预填：
  - 非预期接合 → "释放驻车制动器"
  - 非预期释放/制动不足/接合功能丧失 → "驻车制动器不得释放"
  - 动态制动非预期 → "动态驻车制动不使能"

## 10. 工程判断例外

### C1+低速+驾驶员在车内 → QM

当 S/E/C 查表结果为 A（如 S2/E4/C1=A），但满足以下全部条件时，可工程判断为 QM：
- C=1（简单可控）
- 低速场景（如红绿灯停车、路边停车）
- 驾驶员在车内（可立即踩制动踏板）

填写方式：
- `engineering_override: "QM"`
- `note: "C1+低速+驾驶员在车内，实际可控，工程判断QM"`
- ASIL 由脚本覆盖为 QM

此例外在两个独立项目中一致出现（EPB 08026/02026: S2/E4/C1→QM）。

## 11. 场景预填机制

所有失效模式（含"不足/过大"类）均预填实际场景行并展开 S/E/C，**不使用引用行**。

当一个失效模式的危害事件与另一个失效模式完全相同时（如"驻车夹紧力不足"与"驻车制动无法夹紧"），代码直接复用对应场景列表预填：

```json
{
  "is_reference": false,
  "events": [
    {"scenario": "车辆停在斜坡上（车辆下电）...", "severity": 3, "exposure": 3, "controllability": 3, ...},
    ...
  ]
}
```

- 每个失效模式都有独立的 hazard_id 和事件行
- S/E/C 从参考数据库精确匹配预填
- 不再生成"参考..."引用行

## 12. "不涉及"机制

HAZOP 中 hazard 为"不涉及"或"无整车层面危害"的，prepare 阶段已自动标记 `skip=true`。
Agent 不需要处理这些组，也不生成 HARA 记录。

**QM ≠ skip（重要）**：如果危害描述不是"不涉及/无整车层面危害"，即使 Agent 判断该危害所有场景均为 QM 或 S=0，也**不能**设置 `skip=true`。必须为每个预填场景生成 event，填写 S=0（ASIL 留空，E/C 为 null）或 S>0/QM，并在 description 中说明无危害的理由。QM/S=0 事件仍然写入 HARA 表，只是不分配安全目标。

仅当危害描述本身就是"不涉及/无整车层面危害/无危害"时，才可跳过。validate 会对非"不涉及"但被 skip 的危害组报 warning。

## 13. EPB 动态制动横向运动专项

EPB 动态制动非预期激活除纵向减速外，还可能导致**横向运动**（左右侧制动力不对称）。
此危害需独立展开 4 个场景（见 3.3 节），与纵向减速场景分开：

- 安全目标：`防止车辆非预期横向运动由于动态制动非预期激活`
- 安全状态：`动态驻车制动不使能`
- FTTI：`500ms`

## 14. G 列（危害事件描述）写法

### 有碰撞场景

格式：`失效表现 + 场景条件 + 碰撞后果`

示例：
- "转向助力非预期，车辆不遵循所需的方向，与车辆发生高速碰撞"
- "行驶中EPB非预期接合，车辆发生非预期横向运动，与邻道车辆高速碰撞"
- "坡道停车时EPB非预期释放，车辆溜车，与前方车辆低速碰撞"

### 无碰撞场景

- 车辆静止：`"车辆原地静止，无事故"`
- 高速直线转向丢失/过度/反向/卡滞：`"由于驾驶员没有转弯，无事故"`
- 无法移动：`"车辆在城市道路起步时无法移动，后车绕行，无事故"`

```json
}
```

> 注意：同为高速直线场景，**非预期**助力（系统自主激活）应评 S3/E4/C3=D（见范例 1），而**过度/反向/卡滞**评 S=0。区别在于：非预期助力无需驾驶员输入即可导致突然转向，而后三者需要驾驶员先打方向才会表现。

## 16. S4 完成后的下一步：S5 整车安全目标汇总

`hara validate` 通过并输出 `s4_hara_final.json` 后，**必须继续执行 S5 阶段**，不可在此结束：

```powershell
python scripts/run_hara.py sg generate s4_hara_final.json -o safety_goals.json
```

S5 是纯脚本步骤，从 S4 结果中提取、去重、编号整车级安全目标，生成 `safety_goals.json`。随后在 `write` 命令中传入 `--s5 safety_goals.json`，将整车安全目标写入 Excel 第五个数据 Sheet。

- 规则详见 `references/s5-safety-goal-rules.md`
- 全 QM 域（如 ET 座舱域）可能输出 0 条安全目标，属正常情况，但命令仍须执行
- S5 的 error（例如安全目标描述过短）会在写文件前阻断；必须回到 `s4_hara_agent.json` 修正并重跑 `autofill -> validate -> sg generate`，不得直接修改 final/S5，`--force` 不能绕过
- 详见 `references/agent-workflow.md` 任务F

## 17. 2026-08-25：PT 映射、语义追溯与正式发布门禁

### 17.1 映射不是文本匹配任务

PT 中 `vehicle_hazard_id` / `hazard_family` 是受控工程资产。Agent 不得用关键字、相似度、历史 Excel 或“看起来相近”的危害文本猜测正式映射。`candidate_review`、`unmapped` 只能作为审核候选，`hara validate` 会阻断其进入正式 S4/S5/Excel。

如工程师确认需要新增或选择一个映射，必须以 `engineering_approved` 记录审核人、审核日期和审核单号；它不是 Agent 自行填写的默认状态。

### 17.2 S3→S4 语义主键

每个 S4 危害组及其 event 带有脚本生成的 `semantic_key`，其依据为：

```text
analysis_unit_id + failure_mode + anomaly + vehicle_hazard
```

它用于防止保留相同 `failure_id` / HARA ID 却把异常或危害语义替换成另一条内容。对 PT 正式发布，`hara validate` 必须传入**同一次运行的** `--s3 s3_hazop.json`，脚本会验证 `analysis_unit_id + failure_id + semantic_key` 在 S3 中可追溯。

### 17.3 只允许受控补齐

Agent 完成允许的工程评定后，可运行：

```powershell
python -X utf8 scripts/run_hara.py hara autofill s4_hara_agent.json -o s4_hara_ready.json
```

该命令只补齐追溯元数据；不会创建 event、扩张场景、填写 S/E/C、猜 ASIL 或危害 ID，也不会生成安全目标。不可用任何临时脚本替代该命令。

### 17.4 失败处理原则

验证失败表示链路或工程输入尚未闭合，不表示应该直接修改 JSON 直至“无错误”。按以下顺序处理：

1. 检查 S1/S2/S3 是否真实覆盖当前项目功能、模式、异常和危害；
2. 检查是否错误改写了 exact/compatible 基线的追溯字段；
3. 对新的 PT 危害进入工程审核，保留候选状态；
4. 只有上述输入闭合后，重新执行 `autofill → validate --s3 → sg generate → write`。

### 17.5 needs_review 受控任务表单

PT 的 `create_needs_review_events` 危害组会带有 `agent_task`：这是脚本产生、`hara validate` 强制校验的任务合同。Agent 只能依据其中的 `required_event_fields`、`conditional_rules` 和 `allowed_actions` 完成当前项目事件；`forbidden_actions` 明确禁止猜 `vehicle_hazard_id`、改映射状态或追溯键、修改基线、将旧项目/其他域当成当前事实，以及写临时运行时修复脚本。

因此，`agent_task` 不是说明性备注，不能删除或改写。若需要新的危害映射，走工程审核并使用可审计的 `engineering_approved`，不要在 S4 中篡改任务合同。
