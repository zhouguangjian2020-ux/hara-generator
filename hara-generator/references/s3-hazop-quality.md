# S3 HAZOP 分析质量标准

Agent 执行任务D（S3 HAZOP 分析）时，必须遵循本文档的质量规范。

## 核心规则

1. **覆盖 S2 选中的所有模式** — 不是只做"丢失"，每个选中模式都要枚举异常
2. **按主要安全机制枚举，禁止按内部子功能过度分解** — 见下方"合并原则"
3. **一个异常可对应多个危害** — 多个危害归入同一个 anomaly，最终共用 compose 后置生成的 failure_id
4. **无危害也要列出** — 异常不导致整车危害时，危害写"无整车层面危害"，关联 HARA 写"不涉及"
5. **异常描述 5-15 字，到主要功能级别** — 禁止"功能完全丧失"类泛化，也禁止按内部逻辑过度拆分
6. **危害描述 ≤ 20 字，声明式技术后果** — 禁止因果叙事链

## 枚举策略

### 按功能类型枚举

| 功能类型 | 枚举方式 | 工程师范例 |
|---------|---------|-----------|
| 状态切换（档位、上下电） | 枚举每个状态切换方向 | P→D失效、N→D失效、R→D失效、P→R失效…（动力域档位功能丢失模式有 16 条） |
| 数值输出（扭矩、制动力、温度） | 枚举每个子功能 | 电池包加热丢失、电池包冷却丢失、电机冷却丢失 |
| 执行器动作（EPB、转向） | 枚举每个动作方向 | 接合驻车器丧失、释放驻车器丧失 |
| 安全监测（互锁、绝缘） | 枚举每个监测项 | 高压互锁检测丢失、高压绝缘检测丢失、碰撞下电丢失 |
| 充放电 | 枚举充电/放电各自的电流/电压/电量 | 充电电流过大、充电电压过大、放电电流过大… |

### 每个模式都要覆盖

以 EPB 为例，S2 选中了丢失、非预期、过少、过多：

| 模式 | 子功能枚举 | 条数 |
|------|-----------|------|
| 丢失 | 接合丧失、释放丧失 | 2 |
| 非预期 | 非预期接合（2个危害）、非预期释放、动态制动非预期激活 | 4 |
| 过少 | 驻车制动不足 | 1 |
| 过多 | 驻车制动力过多（无危害） | 1 |

### 合并原则（重要）

"逐子功能枚举"不等于"把每个内部逻辑都建为独立失效模式"。判断标准：**该子功能失效后，整车危害是否与主要功能失效相同？** 如果相同，合并到主要功能，不单独建 FM。

#### 规则

1. **主要安全机制原则**：底盘安全功能（EPB/制动/转向）只按驾驶员可感知的主要动作建 FM，内部辅助逻辑（再夹紧、力调整、温度补偿等）不单独建 FM
2. **同危害合并原则**：同一失效模式下，如果多个子功能导致相同的整车危害，合并为一条异常
3. **功能整体原则**：ABS/EBD 等子功能属于"车辆制动功能"的内部实现，不按子功能拆 FM，以"车辆制动功能"整体建 FM
4. **状态切换例外**：档位控制等状态切换类功能，按具体切换方向枚举（P→D、N→D 等），因为不同方向的危害不同

## failure_id 生成边界

- Agent 只负责异常/危害语义，不生成当前项目运行期 `failure_id`。
- `s3 compose` 在 exact、compatible 和 Agent 数据合并完成后，按 S2 模式顺序及异常语义稳定排序生成 ID。
- Agent anomaly 严禁携带 `failure_id`；无论值是否合法、是否为空或是否带后缀，只要字段存在就阻断 compose。来源案例的 `baseline_failure_id`、`reference_failure_ids` 只用于追溯，不是 Agent 可编辑的运行期编号。
- 两位流水号最多容纳 99 个已分组异常；超过容量必须先修复分组/去重逻辑，不得扩大为三位或让 Agent自行编号。

## 输出后自检

生成 `s3_hazop.json` 后，逐项检查：

1. **模式覆盖**：每个功能的 entries 是否覆盖了 S2 选中的所有模式？
2. **合并检查**：是否有内部子功能（再夹紧、力调整、ABS/EBD子功能等）被单独建为 FM？同危害的子功能是否已合并？
3. **子功能枚举**：每个模式下是否枚举了所有主要功能/状态切换？（对照 docx 章节）
4. **多危害**：一个异常有多个不同危害时，是否拆成了多行（共用 failure_id）？
5. **无危害项**：是否有异常被遗漏因为"觉得没危害"？无危害也要写，标注"不涉及"
6. **异常描述**：每条 ≤ 15 字，到主要功能级别，无"完全丧失"
7. **危害描述**：每条 ≤ 20 字（特殊 ≤ 25），声明式，无因果链
8. **failure_id**：Agent 输入不填写；最终文件中应由 compose 后置生成，格式正确、同一功能内唯一、同一异常多危害共用 ID
9. **功能覆盖**：S1 中标记"是"的功能是否都有对应的 HAZOP entries？（充放电、高压安全等不得遗漏）
10. **associated_hara**：正常留空 `""`，"不涉及"的写 `"不涉及"`

## 2026-08-25：S3 危害 ID 与 S4 映射边界

S3 的职责是描述**当前项目的异常及车辆级危害语义**，不是为了适配某个既有 `PT_HZ_xxx` 编号而修改文本。必须保持下列追溯事实一致：

```text
analysis_unit_id → failure_id → anomaly description → vehicle hazard description
```

- 不得因为 S4 校验报错而回写/改写 S3 的异常或危害文本以“命中”某个 Pack 危害目录；
- 不得根据关键词或文本相似度把新危害强行映射为已有 `vehicle_hazard_id`；
- Pack 明确的 exact/compatible 基线必须保留来源与 `baseline_failure_id`；新项目危害则保留候选状态并进入工程审核；
- “无整车层面危害”“无整车危害”“不涉及”“无危害”或 `N/A` 的 HAZOP，`关联 HARA` 只能为 `不涉及`（兼容输入中的历史值 `否`），不得填“是”或具体 HARA ID。

后续 S4 会从 S3 重算语义主键并做同链验证。若语义尚不能得到工程确认，应保留 `needs_review`，而不是为了通过 S4 验证虚构危害 ID 或安全目标。
